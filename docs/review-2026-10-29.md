## 一、问题清单

### P1 · 会误导结论或阻断使用

**P1-1 没有 pytest 时，11 项端到端测试静默跳过，`npm test` 仍显示全绿**

- 位置：`server/verifier/verify.test.mjs`（`describe.skipIf(!TEST_PYTHON)`）
- 触发条件：机器上没有任何带 pytest 的解释器（新机器、CI 基础镜像、只有 python 无 pytest）
- 后果：另一个 Agent 跑 `npm test` 看到 "47 passed"（实际只剩 36 项），**核心验证一次没跑却显示通过**。这正是这个工具要防的"假绿"，出现在了它自己的测试上
- 复查方式：把 `PROOFPATCH_PYTHON` 指向不存在的路径，同时确保 `D:/ana/python.exe` 不存在，观察测试数量
- 修复方向：无 pytest 时让测试**显式失败**（而非 skip），或在测试结束后输出强制警告并要求 `PROOFPATCH_REQUIRE_PYTHON=1`；另设一个 `npm run test:kernel` 专跑内核

**P1-2 在仓库子目录运行，报错指向 git 内部错误，不指路**

- 位置：`sandbox.mjs:resolveCommit` → `createWorkspace`
- 实测：在 `ProofPatch/test-results/not-a-repo`（非仓库子目录）执行 `check`：
  ```
  错误：无法创建隔离工作区：fatal: '…\not-a-repo' does not appear to be a git repository
  ```
- 根因：`git rev-parse` 会向上找到父仓库，`resolveCommit` 因此成功；直到 `git clone <子目录>` 才失败
- 后果：用户（尤其 monorepo 子包场景）不知道是"目录不对"还是"工具坏了"
- 修复方向：`resolveCommit` 之后加一次 `git rev-parse --show-toplevel`，与 `repoPath` 不一致时提示"当前是子目录，仓库根为 X，请用 `--repo X`"

**P1-3 `patchSource` 强制 `core.autocrlf=false`，与仓库行尾设置可能冲突**

- 位置：`server/verifier/patchSource.mjs`（`status` 与 `diff` 两处均加了 `-c core.autocrlf=false`）
- 触发条件：Windows 上 `core.autocrlf=true`（Git for Windows 默认值）
- 实测：在 `autocrlf=true` 的仓库副本上出现过一次 `ORACLE_TAMPERED`（提示"补丁修改了受保护测试文件"），清理工作区后无法稳定复现，但 `git status` 与 `git diff` 在该配置下确实可能给出不一致的判断
- 后果：可能把整文件误判为改动，进而误伤受保护路径；也可能生成含全文件替换的巨型补丁
- 修复方向：去掉这两处 `-c core.autocrlf=false`，让 `status` 与 `diff` 使用同一套仓库配置

| P2-7 | 中断可能残留临时目录 | `disposeWorkspace` 在 `finally` 中，但 Ctrl+C 直接终止进程时不一定执行；本次检查未见残留，属理论风险 |

## 二、Agent 复现该检查流程的可行性

**结论：可行，但有两个前提，且失败模式不友好。**

复现所需环境：Node ≥ 18、Git、Python + pytest。

一条命令：`npm test`（内核 + 单元），`npm run acceptance -- --python <python.exe>`（8 补丁矩阵）。

障碍：

1. **pytest 必须可被探测到**。否则 `npm test` 会静默跳过 11 项端到端测试（P1-1），Agent 会误判"验证通过"
2. **必须在仓库根目录执行**。子目录场景报错不指路（P1-2）

这两点都不是"跑不起来"，而是"跑起来了但给出错误信息"——比直接崩溃更危险。
