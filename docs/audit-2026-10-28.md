# ProofPatch 判定正确性审查报告

- 审查日期：2026-10-28
- 审查范围：`server/verifier/` 内核 + `bin/proofpatch.mjs` + 补丁生成脚本
- 审查方法：逐文件通读 + 纯函数探针 + 临时 Git 仓库实证
- 依据：`docs/glm-audit.md` 第一轮要求（I1–I6 + 绕过路径 + 误判路径）

---

## 一、不变量核对（I1–I6）

| # | 不变量 | 结论 | 依据 |
|---|---|---|---|
| I1 | 基线必须"稳定失败"；missing/error/timeout 不算失败 | **是**（附脆弱点） | `pytestRunner.mjs:203-208`：exit 5 / "no tests ran" → `missing`；exit 0 要求 `passed > 0` 否则 `missing`；errors 与 fail 分开计数。`verdict.mjs:95-100`：三者任一出现 → `BASELINE_ERROR` → inconclusive |
| I2 | 候选必须"稳定通过"；时好时坏判 rejected | **是** | `verdict.mjs:126-156`：全过→查回归；部分过→`CANDIDATE_UNSTABLE`（rejected）；零过→`CANDIDATE_STILL_FAILING`。注意 repeats=1 时"稳定"不可检测，已在 unproven 披露（`verdict.mjs:204-206`） |
| I3 | 触碰受保护文件必须在执行前拒绝 | **否（文本层成立，补丁层有实锤绕过）** | 文本层：`index.mjs:140-193` 短路发生在任何进程启动前，trials 记为 skipped、repeat=0。但纯重命名可完全绕过（见 F1，已实证） |
| I4 | 判定函数必须是纯函数 | **是** | `verdict.mjs:1-3` 仅导入 describeStrength / normalizeNodeId / REASON_CODES；`decideVerdict` 主体为纯分支，无 IO、无随机、无模型 |
| I5 | verdict 与 reason.code 一致；哈希可独立重算 | **部分** | 一致性：`receipt.mjs` verifyReceipt 按 REASON_CODES 映射校验（有测试）。哈希：canonicalize 键排序、丢弃 undefined，篡改检测经实测。但导出的 JSON Schema 与实际回执存在分歧（F7） |
| I6 | 进程级隔离不得表述为沙箱 | **是** | `sandbox.mjs:17-26` limitations 全量进入回执（`index.mjs:66`）与 unproven（`verdict.mjs:208-212`） |

## 二、问题清单（按"能否导致错误 PROVEN"排序）

### F1 · 纯重命名绕过受保护路径检查 【P0 · 已实证 · 可致错误 PROVEN】

- **位置**：`sandbox.mjs:97-110`（extractPatchPaths 只认 `---`/`+++` 行）；`index.mjs:131-132`（篡改检查只用补丁文本路径）；`index.mjs:241`（树级 changedPaths 已算出，但只写进回执，从未复查）；`patchSource.mjs:87`、`scripts/build-fixture-patches.mjs:178`（两处 diff 均未加 `--no-renames`）
- **触发条件**：补丁包含 100% 相似度纯重命名。git 对这种补丁不输出 `---`/`+++` 行，例如把 `conftest.py` 重命名为 `conftest_backup.py`
- **实证过程**（2026-10-28，临时仓库）：
  ```
  extractPatchPaths(纯重命名补丁) -> []        ← 路径检查看到空数组
  git apply rename.patch        -> 接受
  ls -> conftest_backup.py                      ← 控制面文件已从原位消失
  ```
- **后果**：若基线的 `conftest.py` 正是目标测试失败的原因（严格 fixture、环境准备），把它改名挪走后目标测试"转通过"，篡改检查全程未触发 → **错误 PROVEN**
- **修复方向**：
  1. 两处 diff 生成加 `--no-renames`（重命名展开为删除+新增，路径必然出现在 `---`/`+++` 里）
  2. **权威修复**：`applyPatch` 之后用 `listChangedPaths`（真实 Git 树）重跑 `detectOracleTampering` + `detectControlPlaneChanges`，命中即拒绝。树是 git apply 的实际结果，不依赖文本解析，顺带封死一切手工构造的补丁格式花样

### F2 · 带引号路径的解析缺陷 【P2 · 已探针 · 当前不可利用】

- **位置**：`sandbox.mjs:103`
- **探针结果**：`extractPatchPaths` 对 `+++ b"tests/evil.py"` 提取出 `b"tests/evil.py"`，不匹配受保护路径。但 git apply 层拒绝了一致性不符的形式（`inconsistent new filename`），全引号形式在 Windows 上还被非法文件名字符挡住。**未构成可复现绕过**
- **修复方向**：extractPatchPaths 增加 unquote（防御性）；根治靠 F1 的树级复查

### F3 · 控制面模式过宽 【P1 · 诚实补丁误拒】

- **位置**：`index.mjs:32-40`
- **触发条件**：monorepo 子包自带 `pyproject.toml`、文档示例里的 `tox.ini`、vendored 代码中的 `setup.cfg`——模式匹配树内任何位置
- **后果**：与测试完全无关的合法改动被判 `CONTROL_PLANE_TAMPERED`，诚实补丁被拒。会让真实项目用户第一次使用就放弃
- **修复方向**：只匹配仓库根目录 + pytest 实际 testpaths 范围内的控制面文件；或要求显式列入 oracle.protecting

### F4 · 预存的回归错误永久阻断 PROVEN 【P1 · 已实证 · 诚实补丁被挡】

- **位置**：`verdict.mjs:129-134`
- **实证过程**（纯函数探针）：基线与候选的回归错误完全相同（`errored: ['tests/test_broken.py::test_x']` 两边一致），目标测试 fail→pass：
  ```
  结果 => inconclusive / REGRESSION_ERROR
  期望 => PROVEN（错误未变化，不是候选引入的）
  ```
- **触发条件**：回归范围里有一个与目标无关的坏测试文件（真实项目常见）
- **后果**：修复永远无法被证明，工具在该项目里失去可用性
- **修复方向**：错误也走集合差——复用 computeNewFailures 的逻辑比较 errored，只有**新增**错误才阻断；未变化的错误记入 unproven

### F5 · 多目标 Oracle 的 BASELINE_UNSTABLE 误标 【P1 潜伏】

- **位置**：`verdict.mjs:87-116`（summarizeTrials 跨目标聚合）
- **触发条件**：手写含 2 个 target 的 oracle，其中 target A 恒通过、target B 恒失败
- **后果**：被判 `BASELINE_UNSTABLE`（听起来像 flaky），实际是"A 从未失败"。当前自动推导只生成单目标，故潜伏；契约文件支持多目标，迟早触发
- **修复方向**：按 target 分组判定，逐目标给"未失败/不稳定/稳定失败"

### F6 · missing 场景的误导性明细 【P2 · 已实证 · 结论对但话术错】

- **位置**：`verdict.mjs:158-161`
- **实证过程**：候选三次全 missing（对应源代码 `atexit`+`os._exit(0)` 篡改退出码的攻击）：
  ```
  verdict => rejected ✓（结论正确）
  detail  => "…（fail 0 / error 0 / timeout 0）"   ← 读起来像全过了
  ```
- **后果**：用户看到"fail 0 / error 0 / timeout 0"会以为工具出了 bug，去翻日志才发现是 missing。审计语义上，明细隐瞒了最关键的计数
- **修复方向**：detail 加入 missing 计数，并写明"未收集到结果或退出码异常"

### F7 · JSON Schema 与实际回执分歧 【P2】

- **位置**：`receipt.mjs:234`；`index.mjs:167,210`
- **问题**：schema 的 `patchedTree` 模式 `^git-tree:[0-9a-f]{40,64}$` 会拒绝工具自己产出的 `git-tree:not-computed`（篡改短路场景）。且 schema 未接入任何校验器，"第三方可用 JSON Schema 校验"目前只是声明
- **修复方向**：模式放宽为 `^git-tree:(not-computed|[0-9a-f]{40,64})$`；或提供 `verify-receipt --schema`

### F8 · 非 TTY 静默接受契约 【P2】

- **位置**：`bin/proofpatch.mjs:210-212`
- **问题**：`if (!process.stdin.isTTY) return true;`——管道/CI 里不加 `--yes`，契约确认自动通过。冻结动作没有任何人看过一眼
- **修复方向**：非 TTY 且无 `--yes` 时报错退出，要求显式声明

### F9 · 环境指纹缺目标项目依赖 【P2】

- **位置**：`index.mjs:49-68`
- **问题**：fingerprint 只含 python/pytest/node/平台/隔离后端。两台依赖不同的机器（如 numpy 版本不同）得到同一指纹，回执无法归因
- **修复方向**：fingerprint 纳入依赖清单摘要（`pip freeze` 哈希或 lock 文件哈希）

### F10 · baseCommit 双重解析竞态 【P3】

- **位置**：`check.mjs:37`（首次解析）与 `index.mjs:115`（verifyPatch 内再解析）
- **问题**：check 运行期间用户提交代码，两次 `rev-parse HEAD` 结果不同——契约来自旧基线，trial 跑在新基线上
- **修复方向**：解析一次，把 commit 对象传下去

### F11 · 发现阶段可把导入错误冻结成注定失败的契约 【P3 · 2026-10-28 实测发现】

- **位置**：`check.mjs`（`chosen = failures.find(kind==='fail') ?? failures[0]`）
- **问题**：当基线套件只有**收集/导入错误**、没有任何断言失败时（例如在错误目录里跑、依赖没装），回退到 `failures[0]`（kind 为 error），照样冻结契约。后续 `classifyTargetRun` 会把它归为 `error` → `BASELINE_ERROR` → inconclusive。**不会产生错误 PROVEN**（判定层兜住了），但用户会走完"发现失败→确认契约→跑完→无法判定"全程才得到一个一开始就注定无解的结论
- **实证**：2026-10-27 22:59 有人从 ProofPatch 根目录运行 `proofpatch check`（该目录不是可测项目，fixtures 收集即导入错误），工具照常进入契约流程；只因补丁恰好触碰受保护文件才在控制面短路
- **修复方向**：发现阶段若无 `kind === "fail"` 的失败，明确拒绝（"基线只有错误没有失败，先修环境/换目录"），不进入确认与验证

## 三、验证过且成立的部分（附验证方法）

1. **源代码级退出码篡改不产生错误 PROVEN**。攻击：补丁在被测源码加 `atexit.register(lambda: os._exit(0))`，失败结果被改写为退出码 0。追踪：`pytestRunner.mjs:206` 对 exitCode 0 额外要求摘要里 `passed > 0`，否则归为 `missing` → `verdict.mjs:151-161` → rejected。探针 4 确认。**标注：这条防线是"附带成立"，`passed > 0` 的本意不是防退出码篡改；修 F6 时应把它写成显式规则**
2. **短路路径零执行**。`index.mjs:141-193`：篡改场景不创建工作区、不启动进程；回执 trials 为 1 条 skipped、repeat=0（"未产生任何执行事实"同时写入 unproven）
3. **decideVerdict 纯函数**。文件头导入清单核对（`verdict.mjs:1-3`），无 IO/随机/模型
4. **回执篡改可检测**。`verdict.test.mjs`（改 verdict / 改 trials → 哈希不匹配，各有用例）；`cli.test.mjs`（exit code 契约）；另有 2026-10-27 晚人工实测：改 `baseCommit` 一位 → `verify-receipt` 退出码 1
5. **computeNewFailures 集合差正确**。`verdict.test.mjs` 两个用例：基线本来就红的不算新增；参数化后缀归一化比较
6. **带引号路径攻击被 git 层拦截**（F2 探针，如实记录为"当前不可利用"）
7. **隔离声明如实**。`ISOLATION_PROFILE.limitations` 四条与回执 environment.isolation、unproven 文案逐字段比对一致；"不构成安全沙箱"同时出现在终端输出与回执

## 四、结论

- **能导致错误 PROVEN 的路径：1 条（F1，已实证）**，修复方案明确（树级复查），改动集中在 `index.mjs` 一处 + 两处 diff 参数
- **误拒/误阻断诚实补丁：3 条（F3/F4/F5）**，其中 F4 会直接让工具在含坏测试文件的项目里不可用
- **语义正确但表述误导：2 条（F6/F7）**，恰好都发生在"工具最需要说真话"的位置
- I4（纯函数）、I6（隔离诚实）无问题；I1/I2 成立但各有一条附带成立的防御，应转为显式规则

修复后需重跑：`npm test`（49 项）+ `npm run acceptance`（7 补丁矩阵）+ 新增 F1 复现补丁进矩阵（期望 rejected / ORACLE_TAMPERED 或 CONTROL_PLANE_TAMPERED）。
