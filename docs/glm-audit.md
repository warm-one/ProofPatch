# ProofPatch 外部审查提示词（给 GLM 用）

> 目的：让另一个模型在不了解本项目历史的前提下，独立判断"这个工具会不会给出错误结论"。
> 重点不是代码风格，而是**判定正确性**。

---

## 怎么用

1. 在项目根目录 `D:/vibecoding-shizhan/ProofPatch` 打开 GLM 的代码助手（能读文件的模式）。
2. 把下面「第一轮」整段复制进去。
3. 拿到结果后，用「第二轮」让它把发现的漏洞变成可复现的补丁。
4. 想进一步压测，用「第三轮」做红队视角。

如果 GLM 不能读文件，用最后一节「不能读文件时的替代方案」。

---

## 第一轮：判定正确性审查

```text
你在审查一个名为 ProofPatch 的本地 CLI 工具。它的定位是「独立于 AI Agent 的执行证据层」：

  在隔离环境里复现一个已存在的失败 → 应用候选补丁 → 验证该失败消失
  → 验证没有引入回归 → 产出一份可被第三方校验的证据回执。

它不是代码生成器，也不是静态审查工具。它只回答一个问题：
「这个补丁是真的修复了那个 bug，还是只是让测试变绿了？」

项目根目录：D:/vibecoding-shizhan/ProofPatch

请按顺序读这些文件：
  1. bin/proofpatch.mjs                  CLI 入口（check / verify / verify-receipt）
  2. server/verifier/check.mjs           零配置主路径：自动发现基线失败并推导契约
  3. server/verifier/index.mjs           编排：拦截 → 双克隆 → 基线 N 次 → 候选 N 次 → 回归
  4. server/verifier/verdict.mjs         判定逻辑（声称是纯函数）
  5. server/verifier/receipt.mjs         回执协议、原因码、内容哈希
  6. server/verifier/oracle.mjs          契约校验、强度分级、受保护路径
  7. server/verifier/sandbox.mjs         隔离工作区、补丁应用、树哈希
  8. server/verifier/pytestRunner.mjs    pytest 执行与结果四态分类
  9. server/verifier/discover.mjs        从失败推导契约
  10. server/verifier/patchSource.mjs    工作区改动转补丁

以下是这套工具声称成立的不变量。你的首要任务是判断代码是否真的实现了它们：

I1. 基线必须「稳定失败」才能继续判定；测试不存在、收集错误、超时都不能算作「失败」。
I2. 候选必须「稳定通过」。基线已证明失败稳定后，候选时好时坏应判 rejected。
I3. 补丁触碰受保护测试文件或测试控制面配置时，必须在执行前拒绝，不启动任何进程。
I4. 判定函数必须是纯函数：输入只有观测事实，不包含模型、随机性或启发式。
I5. 回执的 verdict 必须与 reason.code 一致；内容哈希必须能被第三方独立重算校验。
I6. 隔离等级必须如实声明：进程级隔离不能被表述为安全沙箱。

审查要求：

1. 对 I1–I6 每条，给出「是 / 否 / 部分」的判断，并用 文件:行号 说明依据。
2. 最高优先级：找出「看起来实现了、实际能被绕过」的地方。
3. 次高优先级：找出任何可能导致「失败补丁被判为 PROVEN」的路径。
4. 再次：找出可能导致「诚实补丁被误判为 rejected」的路径（这会让人放弃使用）。
5. 明确不评价：代码风格、命名、注释、目录结构、性能。

输出格式，每条问题一行块：

  位置：文件:行号
  触发条件：什么输入/什么补丁会让它发生
  后果：会不会导致错误结论（PROVEN / rejected / inconclusive）
  修复方向：一句话

按「能否导致错误 PROVEN」从高到低排序。
最后附一节「我验证过但没问题的部分」，说明你是怎么验证的——不要只说「看起来没问题」。
```

## 第二轮：把漏洞变成可复现的补丁

```text
基于你上一轮发现的问题，为每一个「能导致错误 PROVEN」的漏洞写最小复现材料。

项目里已有一套对抗补丁可作格式参考：
  fixtures/python-bugfix/patches/            （7 个补丁：honest + 6 个作弊）
  fixtures/python-bugfix/oracles/fix-empty-cart.json
  scripts/build-fixture-patches.mjs          （补丁是真实 git diff 生成的）

对每个漏洞产出：
  1. 一份 unified diff（能干净应用到 fixtures/python-bugfix 的基线）
  2. 说明它会触发哪条不变量失效
  3. 说明当前实现会给出什么结论、正确结论应该是什么

要求：
- 不要修改现有源码，只产出复现材料。
- 如果某个漏洞无法用补丁复现（例如需要特定的 Git 状态），说明触发步骤即可。
- 优先产出「不改任何测试、只改被测代码」就能骗过验证的补丁——这类最危险。
```

## 第三轮：红队视角

```text
现在换个身份：你是攻击者。

目标：让一个「实际上没有修复 bug」的补丁，在 ProofPatch 上获得 PROVEN 结论。

请穷举所有可能的攻击路径，覆盖但不限于：
- 影响测试执行结果（退出码、输出解析、报告改写）
- 影响工作区内容（未跟踪文件、路径穿越、符号链接、换行符）
- 影响契约本身（篡改 Oracle、改受保护路径、利用自动推导的强度下界）
- 影响比较逻辑（回归范围的节点 ID 归一化、参数化测试）
- 影响时序（flaky、并发、超时边界）
- 影响回执（哈希碰撞、字段顺序、规范化序列化边界）

对每条路径给出：
  攻击手法 / 当前是否被防住 / 依据（文件:行号）/ 如果没防住，最小验证方法

最后按「当前实现是否已防住」分成两栏，没防住的那栏按危险程度排序。
```

以下问题**已知**，不需要再报告（但如果你发现它们的修复不完整，请指出）：

| 已知未修 | 回执只有内容哈希，无签名身份，不能证明「由谁生成」 |

## 不能读文件时的替代方案

如果 GLM 只能看粘贴的文本，按这个顺序贴，每次只贴一个文件：

1. `server/verifier/verdict.mjs` —— 最核心，判定逻辑全在这里
2. `server/verifier/index.mjs` —— 流程编排
3. `server/verifier/pytestRunner.mjs` —— 结果分类，最容易出错
4. `server/verifier/sandbox.mjs` —— 补丁应用与路径处理
5. `server/verifier/receipt.mjs` —— 回执协议

把提示词开头改成：

```text
下面我会分批贴上这个项目的源码。在你读完所有文件之前不要下结论。
文件用 === 文件名 === 分隔。
```

## 怎么判断 GLM 的回答有没有用

**有用**的迹象：

- 指出具体文件:行号，并说明什么样的补丁能触发
- 能说出「这个漏洞会让 X 判成 PROVEN」
- 对你列的 I1–I6 逐条给判断，而不是笼统说「整体不错」

**没用**的信号：

- 只谈命名、注释、目录结构
- 说「建议增加更多测试」但不指出哪个分支没覆盖
- 把「已知问题」当成新发现重复一遍
- 提出重构建议但说不出能修复哪个错误结论
